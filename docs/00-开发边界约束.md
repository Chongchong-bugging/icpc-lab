## 1. 效力、解释与引用

### 1.1 效力层级

| 层级 | 文件 | 管什么 | 冲突时 |
|---|---|---|---|
| L1 | 《需求规格》 | 业务事实、字段、流程、阈值、验收 | 业务冲突以 L1 为准 |
| L2 | **本文件** | 范式、范围、技术、领域不变量、数据、质量、流程 | 工程冲突以 L2 为准 |
| L3 | `docs/adr/` 决策记录、设计文档、数据字典 | 实现方案 | 不得违反 L1/L2 |
| L4 | 代码、注释、提交信息、脚本 | 具体实现 | 不得违反以上任意层 |

**GOV-01** 发现 L1 与 L2 冲突：立即停止相关实现，记录冲突点，提交变更单；**不得**由开发者自行选择一方继续。

**GOV-02** L3/L4 不得以"实现方便""性能更好"为由绕过 L1/L2；确需绕过的，走第 11 章例外程序。

**GOV-03** 《需求规格》中标注"建议""待确认"的内容，不因写入代码而升级为已确认规则。

### 1.2 规范动词

| 动词 | 含义 | 违反后果 |
|---|---|---|
| **必须 / 不得** | 强制条款 | 阻断合并与验收 |
| **应当** | 强默认，偏离需 ADR 说明 | 评审记录 |
| **可以** | 允许的实现空间 | 无 |
| **建议** | 参考，不构成验收项 | 无 |

### 1.3 引用义务

**GOV-04** 每个工作包（WP）、每次提交、每条评审意见，必须至少引用以下之一：本文件条款号（如 `DOM-12`）、需求号（`FR-19`）、业务规则号（`BR-09`）、验收场景号（`AT-06`）。**无法引用 = 该变更未获授权**。

**GOV-05** 提交信息格式：`<type>(<scope>): <summary> [FR-xx|DOM-xx]`，type 取 `feat|fix|refactor|test|docs|chore|perf|security`。

### 1.4 术语

| 术语 | 定义 |
|---|---|
| **ReAct** | Reasoning + Acting 的智能体范式。**与前端库 React.js 无关**；本文件在"范式"语境下只用 ReAct 指代该智能体模式，前端仍使用 React。 |
| **WP（工作包）** | 计划的最小执行单元，见 2.7。一个 WP 对应一次可评审的变更。 |
| **Gate（门禁）** | 不可跳过的检查点，见 2.9 与第 8 章。 |
| **安全默认** | 规则未确认时系统采取的保守行为：只记录、只提示、交人工，不自动处罚、不自动选拔。 |
| **规则版本** | 一组阈值与判定口径的不可变快照，业务结果必须绑定当时版本。 |
| **快照** | 业务发生时点的成员/规则/配置副本，后续变更不回写。 |

### 1.5 例外程序

**GOV-06** 任何"临时"偏离必须同时具备：ADR 记录、影响分析、批准人（见人工门禁）、到期日、回归计划。**不得**以"先上线再说"方式长期存在；到期未回归即视为缺陷。

## 2. 开发范式决策：Plan-Execute

### 2.1 项目特征（选型依据）

- 需求已高度结构化：44 条 FR、21 条 BR、8 条 NFR、14 个 AT，**规格本身接近一份计划**。
- 交付分 P0/P1/P2 三阶段，阶段之间有明确门禁与依赖。
- 强合规属性：权限、审批、审计、历史留存，**正确性优先于探索速度**。
- 仍有 15 项待确认问题（Q-01 至 Q-15），部分会反向影响数据模型，**不可能一次性画出完整 DAG**。
- 长周期、多模块、上下文易丢失，必须有**外部化的计划状态**。

### 2.2 候选范式比较

| 维度 | ReAct | **Plan-Execute** | Workflow |
|---|---|---|---|
| 与"规格即计划"的契合 | 低 | **高** | 高（前提是流程已定死） |
| 全局覆盖可证明性（44 条 FR 不漏） | 低 | **高**（计划 + 追溯矩阵） | 高 |
| 阶段门禁与交付节奏 | 弱 | **强** | 强 |
| 对 Q-01…Q-15 未定项的适应 | 高 | **中高**（显式重规划） | 低（改流程=改 DAG） |
| 返工成本 | 中高 | **低** | 高 |
| 状态与上下文管理 | 弱（依赖对话历史） | **强（计划文件即记忆）** | 强 |
| 审计与可追溯 | 弱 | **强** | 强 |
| 单步执行效率 | 高 | 中 | 中低 |
| 失败模式 | 局部正确、全局漏项、范围漂移 | 计划僵化、过度规划 | 流程脆弱、例外无处安放 |

### 2.3 决策

**PAR-01** 本项目采用 **Plan-Execute** 作为唯一的功能开发范式：先形成显式、可评审、可版本化的计划，再按工作包逐项执行、验证、回写。

**PAR-02** 执行阶段允许在**单个 WP 内部**做有边界的试错（读代码、跑测试、局部重构），但**不得**在不更新计划的情况下改变 WP 的目标、范围或验收标准。

### 2.4 否选理由（留档，避免反复讨论）

- **不选 ReAct**：ReAct 擅长"目标模糊、环境未知"的探索，其优势在本项目用不上；而它的弱点——无全局覆盖证明、易范围漂移、依赖上下文记忆——恰好命中本项目最大的风险（44 条 FR 漏项、权限/审计不合规）。以 ReAct 逐条"想到哪做到哪"，P0 结束时无法证明覆盖，返工成本最高。
- **不选 Workflow**：Workflow 把流程固化为 DAG，确定性最好，但本项目 15 项 Q 未定、数据模型尚需迭代，且 P1/P2 范围可能调整。过早固化 DAG 会导致"改一个字段、重画半张图"，且例外场景（补录、代行、外部确认失败）没有合法落点。
- **Plan-Execute 的代价**：计划维护成本与"计划滞后于现实"的风险。用 2.8 的重规划触发条件与 2.9 的门禁控制，成本可接受。

### 2.5 运行循环

```text
        ┌──────────────────────────────────────────────┐
        │  PLAN：选 WP → 读条款/需求 → 写验收与验证命令  │
        └───────────────────┬──────────────────────────┘
                            ↓
        ┌──────────────────────────────────────────────┐
        │  EXECUTE：最小垂直切片，先测试后实现           │
        └───────────────────┬──────────────────────────┘
                            ↓
        ┌──────────────────────────────────────────────┐
        │  VERIFY：类型/ lint / 单测 / 集成 / 权限 / AT  │
        └───────────────────┬──────────────────────────┘
                            ↓
        ┌──────────────────────────────────────────────┐
        │  RECORD：追溯矩阵、ADR、WORKLOG、计划状态      │
        └───────────────────┬──────────────────────────┘
                            ↓
                  有触发条件？──是──→ REPLAN（2.8）
                            │否
                            ↓
                       下一个 WP
```

**PAR-03** 循环六步缺一不可。**未 VERIFY 的 WP 不得标记完成**；未 RECORD 的 WP 视为未完成（下一轮无法安全续接）。

### 2.6 必备工件

| 工件 | 路径 | 作用 | 更新时机 |
|---|---|---|---|
| 计划 | `docs/plan/PLAN.md` | 阶段、WP 列表、依赖、状态、估算 | 每个 WP 状态变化 |
| 追溯矩阵 | `docs/plan/TRACEABILITY.md` | FR/BR/AT → WP → 代码 → 测试 → 状态 | 每个 WP 完成时 |
| 决策记录 | `docs/adr/ADR-xxxx-*.md` | 技术/建模/例外决策及理由 | 决策发生时 |
| 工作日志 | `docs/plan/WORKLOG.md` | 每次执行的命令、结果、阻塞、耗时 | 每个 WP |
| 变更记录 | `CHANGELOG.md` | 面向使用者的功能变化 | 每次合并 |
| 本文件 | `docs/00-开发边界约束.md` | 总约束 | 按第 11 章 |

**PAR-04** 上述文件在 G0 建立；未建立前不得进入 P0 编码（脚手架除外）。

**PAR-05** 计划状态只允许：`proposed → ready → in_progress → review → verified → done`，异常态 `blocked`。`done` 必须由非实现者确认，或由实现者附完整验证证据后自确认并标记待复核。

### 2.7 工作包（WP）定义

**PAR-06** WP 粒度：0.5–2 人日；单次 diff 应能在一个评审会话内读完（经验上限 600 行有效变更）；**一个 WP 只交付一个可验证的业务能力**。

WP 必填字段：

```yaml
id: WP-P0-03
title: 会员任职与任期失效
refs: [FR-01, DOM-03, AT-02]
depends_on: [WP-P0-02]
goal: 一句话说明用户可感知的能力
scope_in: 明确包含
scope_out: 明确不包含
acceptance: 可执行的验收断言
verify: [命令1, 命令2]
rollback: 回滚方式（迁移/开关）
risk: 数据/权限/兼容性风险
```

**PAR-07** 不得把"搭好整个模块"作为单个 WP；必须拆到可验收的垂直切片。

**PAR-08** 涉及数据库结构变更的 WP，必须同时提供迁移、回滚脚本、受影响查询的索引评估。

### 2.8 重规划触发条件

满足任一条件即**必须**暂停执行并重规划：

1. 任一 Q 项定稿，且影响数据模型、状态机或权限；
2. 阶段门禁未通过，且修复需要改设计；
3. 新增/删除 FR，或优先级变化；
4. WP 实际耗时超过估算 2 倍，或阻塞超过 1 个工作日；
5. 发现安全缺陷、数据一致性缺陷或历史数据不可追溯；
6. 计划中的依赖被证明不成立（例如必须引入未批准的外部系统）。

**PAR-09** 重规划产出：影响分析（范围/工期/模型/测试）、计划版本号 +1、追溯矩阵同步、需批准的事项提交人工门禁。**不得**只改代码不改计划。

### 2.9 人工门禁（Human Gates）

| 门禁 | 时点 | 批准内容 | 未通过后果 |
|---|---|---|---|
| **H1 基线** | G0 结束 | 需求基线、技术栈 ADR、领域模型 v1、权限矩阵 v1 | 不得进入 P0 |
| **H2 权限** | 身份与权限模块完成 | 11 类角色的权限点与数据范围 | 不得接入业务模块 |
| **H3 迁移** | 首次迁移合并前；每次破坏性迁移 | 表结构、索引、回滚 | 不得合并 |
| **H4 阶段** | G1/G2/G3 | 范围冻结、验收结果 | 不得进入下一阶段 |
| **H5 扩展** | P2 或外部集成启用前 | 范围、成本、合规 | 功能开关保持关闭 |
| **H6 规则升级** | 任一阈值从"提示"改为"阻断/自动" | 规则依据、误判处理、申诉通道 | 保持提示/人工 |

**PAR-10** H1–H6 的批准必须留痕（评审记录或签字），口头批准无效。

### 2.10 范式红线

**PAR-11** 不得跳过计划直接改业务代码（脚手架、格式化、依赖升级除外）。

**PAR-12** 不得在同一 WP 内顺带实现范围外功能（"顺手做了"一律拆出）。

**PAR-13** 不得用对话记忆代替计划文件；新会话必须能从 `PLAN.md + TRACEABILITY.md + WORKLOG.md` 无损续接。

**PAR-14** 不得伪造验证证据；验证命令与输出摘要必须可复现。

### 3.6 项目级完成定义

1. 23 项 P0 需求全部通过对应 AT 或补充验收用例，追溯矩阵无空行；

4. P1/P2 功能未以"半成品"形式暴露（开关关闭且入口隐藏）；

6. 迁移脚本可在空库重放，种子数据脱敏。

## 4. 技术边界

### 4.1 架构形态

**TECH-01** 采用**模块化单体 + SPA**：一个 API 服务、一个 Web 应用、一个 PostgreSQL、一个对象存储。模块边界按业务域划分（身份、会员、题库、训练、竞赛、审批、统计、系统），**模块间只能通过应用服务接口调用，不得跨模块直连对方表**。

**TECH-02** 不得引入微服务、服务网格、K8s、消息队列、分布式事务。理由：团队规模小、事务一致性要求高、部署环境为单机（Q-13 未定）。

**TECH-03** 后台任务（导入、导出、提醒、到期失效）用数据库任务表 + 进程内调度；单实例部署，任务需幂等。

### 4.2 基线技术栈

> 基线是**默认值**。若课程/部署环境强制其他栈，须在 G0 前以 `ADR-0001` 整体替换，本文件其余条款不变。版本以 lockfile 锁定；大版本升级需 ADR。

| 层 | 基线 | 约束 |
|---|---|---|
| 语言（后端） | Java 21 LTS 语言级别（本机 JDK 25 以 `--release 21` 编译）+ Maven 3.9 | 课程要求；优先 `record`、密封接口、`Optional`；禁止 raw type |
| 语言（前端） | TypeScript 5.x，`strict: true` | 仅 Web 与 shared；不使用 `any` |
| Web | React 19 + Vite 7 + React Router 7 + TanStack Query 5 + Ant Design 5 + ECharts 6 | 服务端状态用 Query；全局 UI 状态最小化 |
| API | Spring Boot 3.5（Spring MVC）+ Spring Security 6 + Spring Data JPA + Bean Validation | 分层：controller → application service → repository；控制器不写业务 |
| 校验 | 后端 Bean Validation 为权威；前端 Ant Design Form + zod 仅做体验 | 同一规则两端各写一次，以接口测试锁定行为 |
| 数据库 | PostgreSQL 16 + Flyway | 约束尽量下沉到 DB；迁移只前进 |
| 认证 | 自建账号 + Argon2id + JWT（访问 15 分钟）+ HttpOnly 刷新 Cookie | Spring Security 过滤器链；见 4.4 |
| 文件 | 本地卷或 MinIO + DB 元数据 + 短时签名 URL | 见 4.5 |
| 测试 | JUnit 5 + MockMvc + Testcontainers（后端）；Vitest + Testing Library（前端）；Playwright（E2E） | 见 7.2 |
| 部署 | Docker Compose + Nginx，单机 | 见 4.6 |
| 契约 | springdoc-openapi 生成 OpenAPI 3.1；前端类型/客户端由契约生成（P1） | 契约变更先改后端注解与测试，再生成前端 |

**TECH-04** 禁止依赖需要公网 SaaS 才能运行的核心能力；禁止引入许可证不兼容（GPL/AGPL 用于闭源分发场景）、无维护、来源不明的包。新增运行时依赖须在 WP 中说明用途与替代方案。

**TECH-05** 后端禁止 raw type、未检查转换与 `System.out` 调试输出；前端禁止 `any`（确需时用 `unknown` + 收窄）、禁止关闭 strict、禁止无理由 `@ts-ignore`；两端均不得空 catch 吞异常。

**TECH-06** 所有时间以 UTC 存储，界面按 `Asia/Shanghai` 展示；业务日历（工作日、节假日、调休）来自可维护配置表，不得硬编码（BR-04、BR-07、BR-11、BR-20 依赖工作日计算）。

### 4.3 仓库结构

```text
apps/api            # Spring Boot API（Java 21，Maven）
apps/web            # React SPA（Vite）
packages/shared     # 前端共享：枚举、权限码镜像、错误码、纯函数
contract/           # OpenAPI 导出与前端生成物（P1）
docs/               # 本文件、adr/、design/、plan/
infra/              # compose、nginx、备份与恢复脚本
scripts/            # 仓库级校验脚本（权限码漂移、契约检查）
```

**TECH-07** `apps/web` 不得被 `apps/api` 引用；`packages/shared` 仅服务前端、不得依赖任何框架运行时；数据库访问只允许出现在 `apps/api`；`apps/api` 不得依赖 Node 包或前端构建产物。

### 4.4 认证与授权实现约束

**TECH-08** 权限模型 = RBAC + 数据范围：`用户 → 角色（可多个）→ 权限点`，角色绑定必须带 `scope_type`（本人/队伍/部门/全局）与有效期。

**TECH-09** 权限点命名 `模块:动作`（如 `member:read`、`training:approve`、`export:member`）。**权威定义**为后端 `PermissionCode` 枚举；`packages/shared` 只做前端镜像；`scripts/check-permissions.mjs` 在 CI 中比对两端集合，漂移即失败。**不得**在控制器散落 `if (role === 'admin')`。

**TECH-10** 每个 API 路由必须声明所需权限点（`@PreAuthorize` 或路由元数据）；CI 中的"路由—权限"元测试必须能枚举全部路由并断言无遗漏。

**TECH-11** 数据范围过滤在 repository/query 层统一注入，不得只在列表接口过滤而详情/导出接口漏过滤。

**TECH-12** 登录限流、失败锁定、会话失效（停用账号立即失效）、刷新令牌轮换。访问令牌只保存在内存，刷新令牌只存 HttpOnly Cookie；**不得**把任何令牌写入 localStorage/sessionStorage。后端以 Spring Security 过滤器链校验，账号停用/角色变更通过 `token_version` 立即失效。

### 4.5 文件与附件

**TECH-13** 文件元数据入库（归属对象、版本、可见范围、上传者、哈希）；访问必须经 API 鉴权后签发短时效 URL；不得暴露存储桶目录。

**TECH-14** 附件可见范围随业务对象权限；对象转移/退出时重新计算，不沿用旧链接。

### 4.6 部署与运维

**TECH-15** 环境：`dev` / `staging` / `prod`，配置经环境变量注入，禁止把密钥写入仓库或镜像。

**TECH-16** 备份：每日全量 + WAL 归档（或等价方案）；备份文件与附件分开保存；每阶段至少一次恢复演练并记录（NFR-06）。

**TECH-17** 生产变更必须可回滚：镜像版本固定、迁移有回滚、功能开关可关。

### 4.7 外部集成策略

**TECH-18** 首期只允许三种集成方式：文件导入、文件导出、链接跳转。任何 API 级对接须先确认接口、权限、责任人与失败补偿（Q-12），并走 H5。

**TECH-19** 外部调用必须有超时、重试上限、失败落库与人工补录入口；**失败不得被记录为"无成绩/无报名"**（DOM-29）。

**TECH-20** API 契约由 springdoc-openapi 从代码生成，纳入 CI 导出与差异检查；前端类型/客户端优先由契约生成（P1）。破坏性契约变更须升 API 版本、同步前端与测试，不得静默改字段语义。

## 5. 领域硬约束

> 本章是业务正确性的核心。每条均可被测试直接断言；违反即为缺陷，不是"体验问题"。

### 5.1 身份与权限

**DOM-01** 学号全局唯一、一人一主档；同一学号不得重复建档（FR-03）。

**DOM-02** 身份必须分维度存储，不得合并为单一"等级"字段：会员生命周期（申请中/备选/正式/退出/除名）、考核状态（待考核/合格/观察）、培养身份（新生/实验室成员/集训队队员）、组织任职、队伍关系。

**DOM-03** 任职与培养身份必须带有效期；到期后权限失效（读取时校验 + 定时任务双保险），历史任职仍可查询（FR-01）。

**DOM-04** 多角色取权限并集，数据范围取并集但受部门/队伍边界约束；越权一律 403，不得静默返回空列表。

**DOM-05** 申请人不得成为本人申请的最终审批人；副会长代行需登记授权范围与期限；系统管理员不自动获得业务审批权。

**DOM-06** 权限校验必须在服务端；前端隐藏只用于体验。导出权限与查看权限分离授权，导出动作单独审计（NFR-02、NFR-04）。

### 5.2 流程与状态

**DOM-07** 申请状态机固定为：草稿、已提交、处理中、退回补正、已通过、已驳回、已撤回。非法迁移必须拒绝；每次迁移写入审批历史（操作者、时间、意见、依据）。

**DOM-08** "审批通过" ≠ "业务生效"：生效时间与生效动作单独记录（退出、报名外部确认、权限调整）。

**DOM-09** 退回补正可修订重提并保留原版本；撤回保留记录，不删除。

**DOM-10** 计划状态机：草稿、待审批、已发布、进行中、已结束、已归档。已发布内容变更生成新版本并通知受影响人员；历史成绩与考核绑定原版本。

**DOM-11** 一律逻辑删除或停用；已产生业务结果的记录不得物理删除（FR-37、BR-21、NFR-04）。

### 5.3 阈值与规则执行方式

| 规则 | 值 | 执行方式 | 依据 | 状态 |
|---|---|---|---|---|
| 拔高师傅同期带徒 | 不超过 3 人 | **阻断确认** | FR-16、BR-09、AT-05 | 已确认 |
| 普及助理教练带新生 | 5–7 人 | **提示 + 说明原因** | FR-16、BR-09 | 已确认（范围） |
| 正式 XCPC 队伍 | 3 人 | **阻断正式确认**；草稿可不满员 | FR-19、BR-13、AT-06 | 已确认 |
| 新生培训（第一学期） | ≥8 次，每次 ≥90 分钟 | 分别统计，不得合并为学时 | BR-06 | 已确认 |
| 寒假任务 | 新生 4 周 | 可配置 | BR-06、FR-18 | 已确认 |
| 第二学期培训 | 12 周任务 | 可配置 | BR-06 | 已确认 |
| 培训计划提交 | 开学后 2 周内 | 到期提醒 + 逾期状态 | BR-05 | 已确认 |
| 培训反馈/总结 | 结束后 3 个工作日 | 提醒 + 逾期 | BR-07 | 已确认 |
| 选拔赛排名与总结 | 结束后 3 个工作日 | 提醒 + 逾期 | BR-11 | 已确认 |
| 集训队退出申请 | 提前 15 个工作日 | 计算并提示 | BR-04 | 已确认 |
| 正赛队伍模拟赛 | 每周 ≥3 次 | 统计 + 提醒 | BR-17 | 已确认 |
| 暑训日历 | 周一至周六训练，周日休息 | 模板，变更需记录原因 | BR-14 | 已确认 |
| 财务共同审批 | 单笔 >500 元 | 双审批（P2） | BR-19 | 扩展范围 |
| 财务公示 | ≥3 个工作日 | 记录 + 提醒（P2） | BR-20 | 扩展范围 |

| 缺勤三次 / 出勤率 <50% | 口径未定 | **仅提示 + 人工待办** | BR-03、Q-04 | 待确认 |

**DOM-12** 所有阈值必须落在 `rule_config`（含值、来源条款、版本、生效区间、执行方式）；代码中**不得硬编码**这些数字。未确认规则只能"提示/人工待办"，**不得阻断、不得自动处罚、不得自动选拔**。

**DOM-13** 逾期不自动判定为不合格；补交保留原截止时间与补交时间（FR-12）。

**DOM-14** 考勤、成绩、完成记录的修改必须留原因、修改人、前后值（NFR-04）。

### 5.4 历史与版本

**DOM-15** 队伍阵容与比赛成绩绑定"当场成员快照"；后续调队不改写历史阵容（FR-19、FR-26、AT-06）。

**DOM-16** 原始提交/导入数据与最终认定结果分开存储；待核实数据不计入已确认统计（§6.2、FR-12）。

**DOM-17** 规则版本随结果固化；修改规则不影响历史结果（NFR-07、DOM-10）。

### 5.5 题库与算法目录

**DOM-18** 目录固定三级：算法大类 → 算法子类 → 知识点；同级名称唯一；支持排序、停用、合并（FR-37、FR-38）。

**DOM-19** 每道正式题**恰好一个主算法**（至少一个，主算法唯一），辅助算法/题型/技巧/来源年份/比赛级别为多标签（FR-40）。

**DOM-20** 前置知识为有向图，保存时检测并拒绝环（FR-39）。

**DOM-21** 被题目、题单或训练记录引用的分类只能停用或合并；合并保留原分类映射，历史题目仍正确显示（FR-37、BR-21）。

**DOM-22** 未审核题可存草稿，**不得**进入正式题单；修订前后内容可追溯（FR-42）。

**DOM-23** 同一 OJ 来源 + 题号重复录入必须提示，不得静默覆盖（FR-07）。

**DOM-24** 导入必须两阶段：预检（成功/重复/错误分类）→ 确认提交；错误行可下载修正；重复提交幂等（FR-41、NFR-05）。

### 5.6 安全、隐私与审计

**DOM-25** 密码使用 Argon2id；不得明文或可逆加密存储；不得在日志中输出凭证（NFR-03）。

**DOM-26** 敏感个人信息（学号、联系方式等）最小化展示；非本人且无授权时掩码；批量导出需单独权限、行数上限与审计（NFR-03）。

**DOM-27** 审计日志 append-only：登录、审批、状态变更、权限变更、成绩/考勤修订、导出、删除。记录操作者、时间、IP、对象、前后值、原因、请求 ID；业务账号无修改/删除权限（NFR-04）。

### 5.7 外部结果

**DOM-28** 校内审核通过与主办方报名成功必须分状态记录；无外部回执时显示"待外部确认"，不得显示"报名成功"（FR-25、AT-08）。

**DOM-29** 外部接口/导入失败不改变业务事实：不得记为无成绩、无报名；进入失败队列并可重试或人工补录。

### 5.8 统计口径（可直接作为断言）

**DOM-30** 题目完成数：按（人员、题目、统计周期）去重的**已核实**完成数；重复提交不重复计数。

**DOM-31** 算法覆盖率 = 周期内完成至少一道有效题的必学知识点数 ÷ 已发布计划中的必学知识点数；分母为 0 显示"不适用"。

**DOM-32** 能力报告：未评估 ≠ 0 分，待核实 ≠ 未完成；缺数据标"未评估"，不得以 0 参与任何合成。

**DOM-33** 任务完成率 = 已完成必做任务数 ÷ 应完成必做任务数；免做/取消/逾期补做是否计入必须可配置；分母 0 显示"不适用"。

**DOM-34** 获奖统计：团队奖按奖项记录去重；按成员统计时另列"人次"，不得把 3 名队员的同一奖项算作 3 个团队奖。

**DOM-35** 训练时长必须区分计划时长、签到时段、自报有效时长；**不得**以登录在线时长代替。

**DOM-36** 报名人数必须按状态分列（提交/校内通过/外部确认/撤回）；团队报名同时展示队数与人数。

## 6. 数据边界

### 6.1 建模原则

**DATA-01** 一实体一主档；关系表必须带有效期或事件时间（任职、队伍、师徒、指导小组）。

**DATA-02** 所有业务结果表必须能回答"依据哪版规则、哪个快照、谁确认"。

**DATA-03** 不使用数据库级联删除业务数据；外键默认 `RESTRICT`，需要级联的仅限纯从属明细（如审批节点）。

**DATA-04** 枚举与字典（部门、岗位、赛事类型、难度、算法分类、审批类型）入库可配置，不得写死在代码里；初始值作为种子数据。

### 6.2 核心实体不变量

| 实体 | 不变量 | 落地 |
|---|---|---|
| 人员 | 学号唯一；一人一主档 | DB 唯一索引 |
| 任职 | 同一人可多岗；有起止时间；到期失效 | 区间校验 + 定时任务 |
| 会员申请 | 状态机 7 态；历史节点不可删 | 状态机服务 + 历史表 |
| 审批实例 | 记录节点、审批人、意见、依据、时间 | 只追加 |
| 学期 | 唯一活动学期；绑定业务日历 | 部分唯一索引 |
| 规则配置 | 版本 + 生效区间；历史结果绑定版本 | 不可变版本行 |
| 算法分类 | 三级；同级唯一；被引用不可删 | 唯一索引 + 引用检查 |
| 知识点前置 | 无环 | 保存时 DFS 检测 |
| 题目 | 每题恰好 1 个主算法 | 关联表部分唯一索引 |
| 训练任务 | 对象类型明确（个人/小组/队伍）；计划版本 | 外键 + 版本 |
| 完成记录 | （任务, 对象, 题目）唯一；原始/认定分离 | 唯一索引 + 状态 |
| 队伍 | 赛季内唯一队名；正式队伍 3 人 | 唯一索引 + 确认校验 |
| 队伍成员 | 加入/退出时间；历史不覆盖 | 区间记录 |
| 比赛成绩 | 关联当场阵容快照 | 快照表 |
| 报名 | （赛事, 组别, 对象）唯一；内外状态分离 | 唯一索引 |
| 文件 | 归属对象 + 版本 + 可见范围 | 元数据表 |
| 审计日志 | 只追加；不可改删 | 权限 + 触发器/只写账号 |

**DATA-05** 上述不变量必须同时在 DB 约束与服务校验中体现；**不得**只靠前端或只靠应用层。

### 6.3 数据库规范

**DATA-06** 表名/列名 `snake_case`；主键 UUID；每表含 `created_at`、`updated_at`；业务表含 `created_by`、`updated_by`。

**DATA-07** 迁移只前进、不修改已发布迁移；每个迁移附带回滚说明；CI 校验迁移可在空库重放。

**DATA-08** 禁止生产环境手工 SQL 改数据；修复必须走迁移或受审计的管理工具。

**DATA-09** 列表查询必须分页，`pageSize` 上限 100；禁止无界查询与 N+1；高频筛选字段建索引并在 WP 中说明。

**DATA-10** 金额用 `numeric(12,2)`；比率用定点或明确精度；不得用浮点做金额/比率累加。

### 6.4 导入导出

**DATA-11** 导入模板版本化；导入任务记录文件哈希、操作者、结果统计、错误明细；同一文件重复提交返回原结果（幂等）。

**DATA-12** 导出必须：走权限、记审计、含筛选条件与行数、异步执行（大文件）、结果短时有效。

**DATA-13** 导出内容与页面看到的数据同源同权限；不得导出未授权字段。

### 6.5 备份与恢复

**DATA-14** 备份策略与恢复目标在 G0 由 Q-13 确认；确认前按"每日全量 + 每周恢复演练"执行。恢复后必须校验：会员、训练、报名、附件关联完整。

## 7. 工程质量门禁

### 7.1 API 契约

**ENG-01** REST，前缀 `/api/v1`；资源名词复数；写操作返回变更后资源或明确结果。

**ENG-02** 统一错误响应：`{ code, message, details?, requestId }`；业务错误码集中定义，不得用 HTTP 200 包裹失败。

**ENG-03** 分页响应：`{ items, page, pageSize, total }`；排序参数白名单。

**ENG-04** 导入等非幂等风险接口必须支持 `Idempotency-Key`；更新接口必须支持乐观锁（`version`），冲突返回 409。

**ENG-05** 所有请求带 `requestId`，日志、审计、错误响应三处一致，便于追查。

### 7.2 测试要求

**ENG-06** 每条 BR/DOM 条款至少 1 个正向 + 1 个反向用例；用例名必须含条款号（如 `DOM-12 rejects auto-disqualification`）。

**ENG-07** 权限：每个 API 至少 1 个 403 用例；另有矩阵测试覆盖 11 类角色 × 关键操作；**不得**在集成测试中 mock 权限层。

**ENG-08** AT-01 至 AT-14 必须各自落地为可重复执行的 E2E 用例，作为 G1/G2 门禁。

**ENG-09** 导入测试固定包含：重复行、错误行、跨页重复、部分成功；断言"不静默覆盖"。

**ENG-10** 测试使用独立数据库（容器或临时 schema），不得连开发库；种子数据脱敏。

### 7.3 CI 门禁（全绿才可合并）

1. 依赖安装使用 frozen lockfile；
2. `tsc --noEmit` 零错误；
3. lint 零 error；
4. 单元 + 集成测试通过；
5. 迁移可在空库重放；
6. 路由—权限元测试通过；
7. 密钥扫描、依赖漏洞（high/critical）检查；
8. Web 构建成功；
9. 涉及 UI 的 WP 附截图或录屏。

### 7.4 完成定义（DoD，逐 WP）

- [ ] 关联 FR/BR/DOM/AT 已填写，追溯矩阵已更新；
- [ ] 验收断言全部有自动化测试或可复现步骤；
- [ ] 权限点已声明，越权用例通过；
- [ ] 审计事件已覆盖（若涉及敏感操作）；

- [ ] 无 TODO/FIXME 遗留在主路径；

- [ ] WORKLOG 记录命令与结果；
- [ ] 无范围外改动。

### 7.5 日志与可观测性

**ENG-11** 结构化日志（JSON），含 `requestId`、`userId`、`route`、`latency`；**不得**记录密码、令牌、完整身份证/联系方式。

**ENG-12** 关键业务事件（审批、状态变更、导出、登录失败）同时写审计表与日志。

## 10. 禁止清单（Deny List）

**DENY-01** 不得以前端隐藏代替服务端鉴权。

**DENY-02** 不得物理删除已产生业务结果的记录。

**DENY-03** 不得把"未评估"当 0 分，不得把"待核实"当未完成。

**DENY-04** 不得依据未确认阈值自动除名、自动取消资格、自动选拔。

**DENY-05** 不得允许申请人审批本人申请，不得让系统管理员默认拥有业务审批权。

**DENY-06** 不得在代码中硬编码部门、角色、阈值、赛事类型、算法分类等业务字典。

**DENY-07** 不得为通过验收而修改测试断言、跳过用例或伪造数据。

**DENY-08** 不得在未更新计划与追溯矩阵的情况下扩大 WP 范围。

**DENY-09** 不得引入范围外模块（OJ、直播、支付、门禁、投票）。

**DENY-10** 不得在无迁移脚本的情况下直接改库结构。

**DENY-11** 不得提交密钥、令牌、真实学生个人信息到仓库。

**DENY-12** 不得在日志、错误响应中暴露堆栈、SQL、凭证。

**DENY-13** 不得用无界查询、无索引筛选、循环内查询支撑列表与统计。

**DENY-14** 不得在控制器/组件中堆业务规则；规则属于领域服务且可测试。

**DENY-15** 不得改写历史审批轨迹、历史署名与历史比赛阵容。

**DENY-16** 不得以"外部接口失败"为由记录无成绩/无报名。

**DENY-17** 不得跳过 H1–H6 门禁发布（包括"仅内网试用"）。

**DENY-18** 不得在同一提交中混入格式化、重命名与业务变更（应拆分）。

## 11. 变更控制

**CHG-01** 本文件遵循语义化版本：删除/收紧约束为 MAJOR，新增约束或范围调整为 MINOR，措辞修正为 PATCH。

**CHG-02** 变更流程：变更单（动机、影响条款、影响 WP、迁移需求）→ 影响分析 → 批准（范围/技术类走 H1/H4/H5，安全类走 H3）→ 更新本文件 + 版本号 + 变更记录 → 通知。

**CHG-03** ADR 模板：背景、决策、备选与理由、影响（正向/负向）、回滚条件、关联条款。

**CHG-04** 每个阶段结束做一次"约束审计"：抽查 10% 的合并，检查是否违反 DOM/DENY/ENG；结果记入 WORKLOG。
